## 2. 双 MAC 事故（根因与教训）

现象：rx1/rx2 双链整夜无法共存——谁后关联 WiFi 谁顶掉对方（路由器侧同 MAC），表现为两块 RX 数据流交替冻结、broker 上两条来自同一 IP 的 TCP、晚上"rx2 一直是 0"的疑难杂症同源。

根因：调试 CSI ESP_FAIL 期间"对齐 esp-radar 初始化"时，在两个 RX 固件里都加了 `esp_wifi_set_mac(WIFI_IF_STA, s_tx_mac)`——把 RX 自身 MAC 设成了 TX 的 `1a:00:00:00:00:00`。该设置对 CSI 采集毫无作用（RX 自身 MAC 与接收广播无关，s_tx_mac 仅用于 CSI 来源过滤），纯负作用。

修复：删除两处 set_mac（出厂 MAC 唯一即可）。**教训：对齐参考实现时逐条审视每个调用的必要性，"照抄初始化序列"会埋跨设备的系统性地雷；多设备同网部署前查 ARP 表可提前暴露 MAC 冲突。**

当晚救急：拔电 rx2 + 断电重启 rx1 → 单链独占 MAC 稳定运行整夜。

## 3. 逐窗指标落库（睡眠质量报告的数据地基）

`backend/app/breath_engine.py` 现随每次 compute 暴露并落库（`csi.db` breath 表新增列，老行 NULL）：

| 列 | 含义 | 用途 |
|----|------|------|
| ratio | 呼吸带谱峰显著度（窗中位） | 有效性的连续度量 |
| band_power | 呼吸带信号功率（top-K 聚合、带通后） | **呼吸暂停代理主判据** |
| raw_std | 带通前聚合幅度标准差 | **体动分型**：体动暴涨 / 暂停不变 |
| loss | 60s 缓冲时间轴缺口占比 | 丢包守卫（>20% 不可信） |

工程坑：INSERT 9 列写 8 个占位符 → 定时器 try-except 吞着每 10s 报错（日志才暴露）；**呼吸 tick 的异常日志要盯**。

## 4. 睡眠质量报告（analysis/tools/sleep_report.py）

```bash
analysis/.venv/Scripts/python.exe analysis/tools/sleep_report.py                 # 自动最近一晚
analysis/.venv/Scripts/python.exe analysis/tools/sleep_report.py --from "..." --to "..."
```
输出 `analysis/output/sleep_report_*.md + .png`（目录已 gitignore，健康数据不进仓库）。

报告结构：数据质量 → 睡眠结构（躺定/入睡点/时长）→ 呼吸（逐小时）→ 体动与觉醒（入睡点后计翻身，分型体动/非体动）→ 呼吸暂停代理 → 整夜图（bpm + 覆盖率 + 功率比曲线）。

**呼吸暂停代理判据**（探索性，非医学诊断）：呼吸带功率 ≤30% 滚动中位(30min) 且 raw_std < 2×滚动中位（排除体动）且丢包 <20%，连续 ≥3 窗（≥30s，30s 分析窗下限决定可靠捕捉 ≥40s 事件）。医学级 10–30s 暂停需原始幅度序列，是后续升级项（板端环形缓冲切片落 SD / amp 定期抽样入库）。

口径修正记录：入睡点只在躺定后搜索；挂起段遇 >60s 数据缺口切断（避免缝成假超长翻身）；睡眠期翻身从入睡点起算。
